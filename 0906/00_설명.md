# 데이터 수집~DB 설계 코드 설명 (0906)

> 목적: "코드가 보고서랑 스무스하게 연결이 안 된다"는 팀원 질문에 답하기 위해,
> **Python으로 무엇을 했고 SQL로 무엇을 했는지**를 코드를 몰라도 순서대로 따라갈 수
> 있게 정리한 문서입니다. `python/`·`sql/` 폴더의 파일은 실제 운영 코드를
> 그대로 복사한 것이며(로직 변경 없음), 각 파일 상단에 원본 경로를 배너로 남겨뒀습니다.

---

## 0. 가장 먼저 알아야 할 것 — 파이프라인이 사실 두 갈래입니다

이 프로젝트의 데이터 파이프라인은 **완전히 하나의 흐름이 아니라 두 갈래**입니다.
발표할 때 이 구조를 먼저 짚어주면 "왜 파이썬 코드랑 SQL 파일이 따로 노는 것처럼
보이는지"가 바로 설명됩니다.

```text
[갈래 A] 실제 운영 파이프라인 (진짜 DB를 만드는 코드)
  Python 수집 (01, 02) → Python 전처리·정제·적재 (03) → data/aging_infra.db

[갈래 B] SQL 정제 파이프라인 (검증·시연용, sql/00~17)
  data/raw/ 원본 CSV → SQL만으로 똑같은 로직을 재현 → 결과가 갈래 A의 DB와
  값까지 100% 일치하는지 대조 검증 완료
```

즉 **실제로 지금 쓰는 `data/aging_infra.db`를 만드는 건 갈래 A(Python)** 이고,
**갈래 B(SQL 00~17)는 "SQL로도 똑같이 할 수 있다"는 걸 보여주기 위해 나중에
별도로 만든 재현판**입니다. 두 갈래가 서로 다른 파일인데 결과는 같다 — 이 한 문장이
발표 대본의 핵심 연결고리입니다.

## 1. [갈래 A-1] Python 데이터 수집

### `01_collect_estat_japan.py` — 일본 e-Stat API

- 일본 총무성 통계국 e-Stat API에서 인구·병상수·요양시설수 3종을 수집.
- 인구는 원래 국세조사(5년마다, 2015·2020년만 존재) 대신 **인구추계(統計表010)**
  통계표로 바꿔서 2015~2024년 매년 데이터를 확보(2015~2019는 2015년 국세조사 기준
  시리즈, 2020~2024는 2020년 국세조사 기준 시리즈를 이어붙임).
- e-Stat API는 한 번에 최대 10만 건까지만 주기 때문에, 필요한 항목만 콕 집어
  요청(`cdCat01`)하고 페이지네이션으로 나머지를 받는 방식으로 데이터 누락을 방지.

### `02_collect_kosis_korea.py` — 한국 KOSIS Open API

- 한국 국가데이터처 KOSIS API에서 고령인구비율, 장기요양기관현황, 의료기관병상수
  3개 통계표를 수집.
- 장기요양기관현황처럼 지역 외에 분류축이 하나 더 있는 통계표는 `objL2`까지
  요청해서 "계(합계)"와 세부 시설유형(방문요양·노인요양시설 등) 행을 구분할 수
  있게 `category2` 컬럼을 남겨둠 — 이걸 안 남기면 나중에 전처리 단계에서
  가짜 중복행이 생김(2026-08-24 (3)에 발견·수정된 버그).

**여기서 나오는 결과물**: `data/raw/` 아래 원본 CSV 7개(정제되지 않은 원자료).

## 2. [갈래 A-2] Python 데이터 전처리·적재

### `03_preprocess_and_load.py` — 원본 CSV → 정제 → SQLite 적재

`docs/기획서.md` 2.3절 "데이터 전처리 계획" 표와 1:1로 대응하는 실제 구현입니다.
2026-09-06에 표를 실제 코드에 맞게 다시 정리했으니, 발표 때는 이 표를 그대로
따라가면 됩니다.

| 순서 | 하는 일 | 코드 위치 |
|---|---|---|
| 1 | 수치형 컬럼 변환 + 항목 필터링(범주값 통일, 중복 방지) | `load_korea()`, `load_japan()` |
| 2 | 컬럼명 매핑 (KOSIS/e-Stat 원본명 → 공통 영문명) | 각 함수의 `rename()` |
| 3 | 한·일 병합 + 기간 통일(2015~2023, 결측 사전 차단) | `pd.concat`, `YEARS` 필터 |
| 4 | **이상치 확인** (2026-09-06 신규 추가) | `check_outliers()` |
| 5 | 파생변수 생성 (인구 1만명당 병상수·요양기관수, 인구증감률) | `add_derived_columns()` |
| 6 | Dim/Fact 테이블 구성 → SQLite 적재 | `build_dim_region()`, `build_fact()`, `load_to_sqlite()` |

> ⚠️ **이 스크립트가 만드는 건 여기까지입니다.** "인프라 격차지수"는 여기서
> 계산되지 않습니다 — 4번에서 다룹니다.

## 3. [갈래 B] SQL 정제 파이프라인 (00~17번, 검증·시연용)

`sql/` 폴더의 00~17번은 위 2번(Python)이 하는 일을 **SQL 문법만으로 다시 구현**한
것입니다. 실제 채점 기준(SQL/DB 설계 15점)에서 "SQL로 정제한 흔적"을 보여주기
위해 별도로 만들었고, 결과가 운영 DB(`aging_infra.db`)와 완전히 같은지 값 단위로
대조까지 마쳤습니다.

18개 파일은 아래 6단계로 묶입니다 — 발표할 때 파일 하나하나가 아니라 이 6단계로
설명하면 훨씬 매끄럽습니다.

| 단계 | 파일 | 하는 일 |
|---|---|---|
| ① 원본 스키마 | `00_create_raw_tables.sql` | 원본 CSV 7개를 담을 raw_* 테이블 생성 + 일본 지역명 한글 매핑표 |
| ② 정제 (소스별 1:1) | `01`~`07` (7개) | 일본 인구/병상수/요양시설, 한국 고령화율/병상수/요양기관/주민등록인구 — 소스마다 개별 정제 |
| ③ 병합 | `08_merge_korea.sql`, `09_merge_japan.sql` | 국가별로 정제된 소스 3개를 JOIN |
| ④ 통합·기간 필터 | `10_combine_and_filter_years.sql` | 한/일 UNION ALL + 2015~2023 필터 |
| ⑤ 파생컬럼 | `11_add_derived_columns.sql`, `12_add_pop_change_rate.sql` | 고령화율·1만명당 지표, 인구증감률(self-JOIN) |
| ⑥ ERD 조립 | `13`~`17` (5개) | Dim_Country → Dim_Region → Dim_Date → Fact_RegionStats → 뷰(Fact_Population/Infra) 순서로 최종 테이블 조립 |

### `00-1_create_tables_ddl.sql` — DB 설계(스키마) 원본

이건 sql_cleaning 00~17번과는 별개로, **실제 운영 DB의 테이블 구조 정의**
(`sql/ddl/create_tables.sql`)입니다. Dim_Country/Dim_Region/Dim_Date/
Fact_RegionStats + Fact_Population/Fact_Infra(뷰) 스키마가 여기 있습니다.
발표에서 "DB 설계"를 보여줄 땐 이 파일을 기준으로 삼으면 됩니다.

## 4. 인프라 격차지수는 어디서 계산되나? — `18_infra_gap_index_분석단계.sql`

이 파일은 sql_cleaning의 00~17번과 **번호는 이어지지만 실제로는 다른 단계**입니다
(원본은 `sql/analysis/q5.sql`). 00~17번이 "원본 → 정제 → DB 적재"까지라면, 이
파일은 그 DB가 다 만들어진 **다음**, 분석 질문에 답하기 위해 실행하는 쿼리입니다.

- 고령화율 순위 − 인프라밀도(병상수+요양기관수) 순위 = 인프라 격차지수
- 이 파일은 **전역(64개 지역 통합) 순위** 기준입니다 — 국가별로 나눠서 보는 버전은
  `scripts/visualize.py`가 별도로 `PARTITION BY country`를 써서 계산합니다.
  (전역 순위로 보면 취약 지역 상위권이 전부 일본으로 쏠리는 현상이 있어서, 국가별
  순위로 다시 봐야 한다는 게 이 프로젝트의 핵심 Insight 중 하나입니다.)

## 5. 발표용 한 문단 요약 (그대로 읽어도 됨)

> "저희는 먼저 Python으로 e-Stat·KOSIS API에서 원본 데이터를 수집하고, 같은
> Python 스크립트 안에서 정제·파생변수 계산까지 마친 뒤 SQLite DB에 적재했습니다.
> 그리고 이 DB 설계와 SQL 분석 역량을 별도로 보여드리기 위해, 원본 CSV부터 최종
> 테이블까지 가는 과정을 SQL만으로도 똑같이 재현한 파이프라인(00~17번 파일)을
> 추가로 만들었고, 두 결과가 값 단위로 100% 일치함을 확인했습니다. 이후 분석
> 단계에서는 고령화율과 인프라 밀도 순위를 비교해 인프라 격차지수를 계산했고,
> 이걸 전역 순위로 보느냐 국가별 순위로 보느냐에 따라 결론이 달라진다는 게 저희
> 프로젝트의 핵심 발견 중 하나입니다."

모든 파일은 원본 로직을 바꾸지 않은 복사본이며, 상단에 원본 경로가 배너로
남아 있습니다. 실제로 코드를 수정해야 할 일이 생기면 **원본 경로(`scripts/`,
`sql_cleaning/`, `sql/`)를 고쳐야** 운영 DB·팀 공유 산출물에 반영됩니다 — 이
폴더는 설명·발표용 사본입니다.
